# VYRO — وایرو

شبکه اجتماعی فارسی با رابط راست‌چین، طراحی تیره و رنگ شاخص لیمویی.

## وضعیت فعلی
این مخزن شامل پایه اولیه رابط React/Vite، اتصال اختیاری Supabase و گردش‌کار ساخت APK اندروید است. این نسخه هنوز محصول نهایی نیست؛ پیام‌رسانی، استوری واقعی، رسانه‌ها، لایک‌ها و پنل مدیریت کامل باید جداگانه پیاده‌سازی و آزمایش شوند.

## پیش‌نمایش محلی
- Node.js 20 یا جدیدتر
- `npm install`
- `npm run dev`

## تنظیم Supabase
در تنظیمات مخزن GitHub، به **Settings → Secrets and variables → Actions** برو و این Repository secrets را اضافه کن:
- `VITE_SUPABASE_URL` = آدرس پروژه Supabase
- `VITE_SUPABASE_PUBLISHABLE_KEY` = کلید publishable پروژه

هرگز کلید `service_role` یا secret را در برنامهٔ فرانت‌اند قرار نده.

## ساخت APK از طریق GitHub Actions
از تب **Actions**، گردش‌کار **Build VYRO Android APK** را انتخاب کن و روی **Run workflow** بزن. پس از موفقیت، artifact با نام `vyro-debug-apk` را از اجرای workflow دریافت کن. APK فعلی از نوع debug و برای آزمایش است، نه انتشار نهایی در فروشگاه.

## دسترسی هنگام محدودیت اینترنت بین‌الملل

هدف وایرو این است که تا وقتی شبکهٔ داخلی برقرار است، سرویس‌های اصلی از backend قابل‌دسترسی داخلی استفاده کنند؛ نه اینکه فقط رابط محلی نمایش داده شود. معماری، محدودیت‌های فعلی و مراحل استقرار در [راهنمای دسترسی از شبکه داخلی](./docs/DOMESTIC_NETWORK_FA.md) توضیح داده شده است. این قابلیت هنوز تا زمان استقرار backend در شبکهٔ هدف و آزمایش واقعی، تأییدشده نیست.

## امنیت
پیش از استفاده عمومی، سیاست‌های RLS در Supabase—به‌ویژه جلوگیری از تغییر نقش کاربر و اطمینان از عضویت در گفتگو پیش از ارسال/خواندن پیام—باید بازبینی و سخت‌سازی شوند.


## ثبت‌نام فقط با کد دعوت

1. در Supabase برو به **SQL Editor → New query**.
2. فایل [supabase/invitation_only_signup.sql](./supabase/invitation_only_signup.sql) را از مخزن باز کن، تمام SQL آن را کپی کن و اجرا کن.
3. برای تست اولیه، کد دعوت **VYRO-START-2026** با ظرفیت ۲۵ استفاده ساخته می‌شود. بعداً از SQL Editor می‌توانی کدها را تغییر بدهی. جدول کدها عمداً برای کاربران عادی قابل خواندن نیست؛ بررسی و مصرف کد توسط trigger سمت دیتابیس انجام می‌شود.
4. در GitHub برو به **Settings → Secrets and variables → Actions** و مطمئن شو این دو Repository secret تنظیم‌اند:
   - **VITE_SUPABASE_URL** = https://drwnfifwvyfplsiqnvlp.supabase.co
   - **VITE_SUPABASE_PUBLISHABLE_KEY** = کلید publishable / anon پروژه Supabase (نه service_role)
5. پس از تنظیم Secrets، از **Actions → Build VYRO Android APK → Run workflow** ساخت تازه را اجرا کن.

## وضعیت نسخه آزمایشی جدید
- تب «خانه» حذف شده و «+» داخل اکسپلور قرار دارد.
- چت‌ها پیام‌های آزمایشی جداگانه دارند؛ انتخاب گفتگو وارد صفحه اختصاصی آن می‌شود و دکمه بازگشت، فهرست گفتگوها را نشان می‌دهد.
- ساخت گروه و کانال فعلاً محلی/نمایشی است و تا پیاده‌سازی backend چت، آنلاین نیست.
- موسیقی، دستیار هوشمند، استوری و امکانات رسانه‌ای به‌صورت بخش‌های قابل مشاهده ولی غیرفعال نشان داده می‌شوند.
- کادر نئونی متحرک و تنظیمات پایه در نسخه آزمایشی اضافه شده‌اند.
- ثبت‌نام با کد دعوت توسط trigger دیتابیس کنترل می‌شود؛ اجرای فایل SQL بالا برای فعال‌شدن این الزام ضروری است.
- پیام‌رسانی زنده، عضویت گروه/کانال، لایک‌های ذخیره‌شده و مدیریت کامل هنوز به backend و سیاست‌های RLS نیاز دارند.


## ساختار بخش Muzio (مرحلهٔ طراحی، بدون وابستگی اجباری به Spotify)

Muzio در وایرو یک بخش مستقل برای موسیقی است و فعلاً نباید به فعال بودن Spotify Web API وابسته باشد. تا زمان تعیین مسیر قانونی و فنی ارائهٔ کاتالوگ موسیقی، رابط و مسیرهای کاربری باید قابل نمایش بمانند.

### صفحهٔ اصلی
- هدر Muzio با جست‌وجوی آهنگ، خواننده و آلبوم؛ اگر سرویس جست‌وجو هنوز در دسترس نیست، پیام وضعیت روشن نمایش داده شود.
- بخش‌های «کشف آهنگ»، «کتابخانهٔ من» و «حساب متصل»؛ اتصال حساب فقط وقتی فعال شود که تنظیمات و دسترسی لازم واقعاً آماده باشند.
- کارت آهنگ شامل تصویر/کاور، نام آهنگ، نام هنرمند، منوی بیشتر، اشتراک‌گذاری و اقدام پخش در صورت وجود منبع مجاز.
- پخش‌کنندهٔ کوچک و نوار پخش با نام آهنگ فعلی؛ از نمایش کنترل‌های پخش غیرواقعی برای آهنگ‌هایی که پخش مجاز ندارند خودداری شود.

### کتابخانهٔ کاربر
- آهنگ‌های پسندیده‌شده
- پلی‌لیست‌های ذخیره‌شده و امکان ساخت پلی‌لیست محلی/داخلی وایرو
- آهنگ‌ها یا فایل‌های صوتی انتخاب‌شده از دستگاه، در صورت پشتیبانی مرورگر
- وضعیت خالی مناسب وقتی هنوز چیزی ذخیره نشده است

### ارتباط موسیقی با بخش‌های دیگر وایرو
- ارسال کارت موسیقی به گفت‌وگوی خصوصی یا گروه، به شکل لینک/کارت اشتراک‌گذاری
- افزودن موسیقی به بخش Muzio پروفایل کاربر
- باز کردن منبع اصلی موسیقی در سرویس ارائه‌دهنده، وقتی پخش داخلی در دسترس نیست

### ترتیب پیاده‌سازی
1. ساختار رابط و حالت‌های خالی/نمونه، بدون وابستگی به Spotify.
2. آماده‌سازی کتابخانهٔ داخلی، پسندیدن و پلی‌لیست‌های وایرو.
3. اتصال جست‌وجو و حساب Spotify فقط پس از تأیید دسترسی API و تنظیم Redirect URI.
4. آزمایش در نسخهٔ وب؛ انتقال به Android فقط پس از تأیید صریح کاربر.

### محدودیت فعلی
Spotify Web API در داشبورد کاربر غیرفعال است و حساب Premium ندارد. بنابراین نباید ادعا شود که جست‌وجوی Spotify، اطلاعات شخصی، پلی‌لیست‌های حساب یا پخش کامل موسیقی در حال حاضر فعال و آزمایش‌شده‌اند.


## موتور هوشمند کشف موسیقی (طرح پیاده‌سازی)

### هدف تجربهٔ کاربر
- جست‌وجو فقط روی محتوای مرتبط با موسیقی انجام شود؛ نتایج به شکل کارت آهنگ با عنوان، کانال/هنرمند، تصویر بندانگشتی، مدت‌زمان در صورت دسترسی و منبع نمایش داده شوند.
- با انتخاب نتیجه، ابتدا از پخش‌کنندهٔ رسمیِ قابل‌تضمین همان منبع استفاده شود؛ اگر امکان پخش درون‌برنامه‌ای وجود نداشت، دکمهٔ «بازکردن منبع اصلی» نمایش داده شود.
- موتور می‌تواند چند نتیجه را رتبه‌بندی کند و بر اساس تطابق نام آهنگ/هنرمند، ارتباط موسیقایی، کیفیت منبع و قابلیت پخش مجاز، نتیجهٔ مناسب‌تری را بالاتر نشان دهد. هیچ نتیجه‌ای نباید به‌عنوان «بهترین سایت» قطعی معرفی شود مگر شواهد قابل اتکا وجود داشته باشد.
- از استخراج فایل صوتی، دورزدن محدودیت سایت‌ها، دانلود غیرمجاز یا scraping خلاف شرایط سرویس استفاده نشود.

### منبع اولیهٔ پیشنهادی
- به‌جای اتکا به جست‌وجوی عمومی HTML گوگل، امکان استفاده از YouTube Data API بررسی شود؛ این API جست‌وجوی ویدئو را با فیلترهایی مانند type=video، videoEmbeddable=true و موضوع موسیقی پشتیبانی می‌کند. نتیجه باید در چارچوب مجوزها و شرایط YouTube نمایش داده شود.
- پخش فقط با پخش‌کنندهٔ رسمی YouTube یا منبعی که اجازهٔ پخش را می‌دهد انجام شود؛ وجود نتیجه در جست‌وجو به معنی اجازهٔ استخراج فایل یا پخش مستقیم صوتی نیست.
- Google Custom Search JSON API مسیر مناسبی برای پیاده‌سازی تازه نیست، چون مستندات جاری گوگل می‌گوید برای مشتریان جدید بسته است؛ در صورت نیاز به جست‌وجوی گستردهٔ وب باید گزینهٔ رسمیِ در دسترس در زمان پیاده‌سازی بررسی شود.

### معماری پیشنهادی
1. رابط Muzio یک لایهٔ جست‌وجوی مستقل از ارائه‌دهنده داشته باشد.
2. یک سرویس سمت سرور/Edge Function کلیدهای API را نگه دارد؛ کلید محرمانه داخل کد مرورگر قرار نگیرد.
3. نتایج از چند فیلتر عبور کنند: مرتبط‌بودن با موسیقی، تطابق عنوان/هنرمند، تکراری‌نبودن و قابلیت پخش/نمایش قانونی.
4. رابط، نتیجه‌ها و وضعیت‌های «در حال جست‌وجو»، «نتیجه‌ای نیست»، «پخش در اینجا در دسترس نیست» و «بازکردن منبع» را واضح نشان دهد.
5. ابتدا فقط در وب آزمایش شود؛ Android پس از تأیید صریح کاربر تغییر کند.

### وابستگی‌ها و وضعیت
این بخش فعلاً طرح فنی است، نه قابلیت پیاده‌سازی‌شده یا آزمایش‌شده. فعال‌سازی YouTube Data API ممکن است به ساخت پروژهٔ Google Cloud، فعال‌کردن API و ساخت API key نیاز داشته باشد. قبل از ساختن این اتصال باید محدودیت سهمیه، شرایط سرویس و دسترسی واقعی حساب بررسی شود.
